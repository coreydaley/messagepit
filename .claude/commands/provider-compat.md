# /provider-compat

Audit how closely the MessagePit stub for `$ARGUMENTS` matches the real provider API.

## Provider Registry

| Name       | Package path           | Port | Spec source |
|------------|------------------------|------|-------------|
| sendgrid   | internal/sendgrid/     | 8101 | https://raw.githubusercontent.com/sendgrid/sendgrid-oai/main/oai.json |
| mailtrap   | internal/mailtrap/     | 8100 | https://api-docs.mailtrap.io/docs/mailtrap-api-docs/send-emails-email-sending-api |
| twilio     | internal/twilio/       | 8200 | https://raw.githubusercontent.com/twilio/twilio-oai/main/spec/json/twilio_api_v2010.json |

## Workflow

### 1. Resolve Provider

Parse `$ARGUMENTS` as a provider name (lowercase). If not in the registry above, print the registry table and exit.

### 2. Infer Claimed Scope

Read the provider's handler file (`internal/<name>/<name>.go`) and any additional `.go` files in that package. From the source, extract:

- **Endpoints**: every HTTP method + path registered (`r.HandleFunc(...)`, `mux.HandleFunc(...)`, or similar)
- **Auth scheme**: how `Authorization` is checked (Bearer token, Basic, API key header, etc.)
- **Request fields**: struct field names and JSON tags in the request body type(s)
- **Response shapes**: status codes returned, response body structure (struct, plain status, JSON object)
- **Error codes**: every distinct HTTP status code the handler can return

Summarize as a **Claimed Scope** block — this is the contract the twin asserts it fulfills.

### 3. Fetch the Real Spec

Delegate to the `spec-analyst` subagent (`.claude/agents/spec-analyst.md`), passing:
- The spec URL from the registry
- The claimed scope extracted in step 2

The subagent returns a **Spec Snapshot** — the subset of the real spec that corresponds to the claimed endpoints/fields. This keeps the large spec payload out of the main context.

If no subagent is available, fetch the spec inline, extract only the relevant paths, and continue.

### 4. Generate `compat_test.go`

Write `internal/<name>/compat_test.go`. This file is **fully regenerated** on every run — treat it as owned by this command, never hand-edited.

The file header must contain:

```go
// Code generated by /provider-compat. DO NOT EDIT.
// Re-run: /provider-compat <name>
```

Generate one test per claimed endpoint. Each test:

1. Builds the exact request the real spec requires (method, path, headers, body shape)
2. Posts it to a local `httptest.NewServer` wrapping the provider's handler
3. Asserts the response status code matches the spec
4. Asserts the response body shape matches (presence of required fields, correct content-type)
5. Tests one known error case per endpoint (e.g., missing auth → 401, malformed body → 400)

Use table-driven tests where multiple cases share a handler setup. Name each test `TestCompat_<Method>_<PathSuffix>`.

Do **not** duplicate tests already in `<name>_test.go` — compat tests cover spec conformance; behavioral tests live in the human-owned file.

### 5. Run the Tests

```bash
go test ./internal/<name>/... -run TestCompat_ -v 2>&1
```

Capture output. Note pass/fail per test.

### 6. Report

Print a fidelity report:

```
=== Provider Compat Report: <name> ===

Claimed scope
  Endpoints : <list>
  Auth      : <scheme>
  Fields    : <count> request fields, <count> response fields

Spec coverage
  Matched   : <n>/<total> claimed endpoints found in spec
  Gaps      : <list any claimed items not in spec — possible drift>

Test results
  Passed    : <n>
  Failed    : <n>
  <details for each failure with spec citation>

Not yet claimed (spec endpoints not implemented)
  <list paths from spec outside claimed scope>

Fidelity score: <passed>/<total compat tests> (<percent>%)
```

If all tests pass, end with: `Twin is in sync.`
If any fail, end with: `Action required: see failures above.`
